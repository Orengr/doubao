# 限流问题与保活策略（重要教训）

## 事件记录（2026-11-16 02:22 ~ 02:50）

### 现象
豆包账号被整体限流，发送任何消息都返回：
```json
{"error_code":"710022004","error_msg":"rate limited",
 "extra":{"decision":"{\"from\":\"shark_admin\",\"type\":\"verify\",\"subtype\":\"semantic_reasoning\"}"}}
```

### 根因
**保活间隔设得太短（60-90 秒），连续发送 380+ 条消息，把账号撞进限流。**

时间线：
- 01:51 保活启动，间隔 60-90 秒
- 02:22 开始出现「发送无有效回复」
- 02:27 沙箱被回收（保活失效，无法唤醒）
- 02:42 累计 382 次发送，全部失败
- 02:50 测试确认：发「你好」也返回 rate limited

### 结论
- **这不是代码 bug，是账号级限流**
- 限流恢复时间未知（通常几小时到 24 小时）
- 高频保活是**反效果**：越失败越发，越发越限流

## 正确的保活策略

| 参数 | 错误值 | 正确值 | 原因 |
|---|---|---|---|
| 发送间隔 | 60-90 秒 | **240-360 秒**（4-6 分钟） | 60 秒太频，必撞限流 |
| 失败处理 | 继续按原间隔发 | **指数退避**（+120s，上限 900s） | 越失败越发 = 越限流 |
| 连续失败上限 | 无 | **5 次后暂停 30 分钟** | 避免刷屏 |
| 隧道重连 | 3 秒判定 | **5 秒判定，无冷却** | 避免抖动误判 |
| 消息内容 | 固定长命令 | **极简短句**（如「1+1=?」） | 长命令易触发内容审核 |

## 恢复限流的办法

1. **立即停止所有发送**（`systemctl stop ka-pure`）
2. 等待 2-24 小时（观察 `710022004` 是否消失）
3. 恢复后**先用 1 条消息测试**，成功再开启保活
4. 保活间隔设为 4-6 分钟，不要更短

## 判断是否恢复

```bash
# 发一条测试消息，看返回
python3 /root/ka_once.py
# 如果日志出现「SSE_ACK」= 恢复了
# 如果还是「发送无有效回复」= 还在限流
```

## 沙箱回收与保活的关系

沙箱被回收的直接原因是**保活失败后无法唤醒**：
- 保活能发 → 沙箱活跃 → 不被回收
- 保活被限流 → 无法发送 → 沙箱闲置 → 被回收

所以**保活间隔要平衡**：
- 太短（60 秒）→ 撞限流 → 失效 → 沙箱被回收
- 太长（30 分钟）→ 沙箱闲置 → 被回收
- **4-6 分钟是经验最优**

## 备用唤醒手段

如果保活被限流，还有这些办法：
1. **手动在豆包 App/网页发一条消息**（人工唤醒）
2. **等待用户下次使用豆包**（自然唤醒）
3. 保活恢复后自动接管
